# Dataset guide

## 1. Directory layout

A dataset directory contains five CSV files:

```text
data/my_dataset/
├── users.csv
├── businesses.csv
├── services.csv
├── business_services.csv
└── interactions.csv
```

All identifiers are strings. Extra columns are ignored; the loader only requires the
columns listed below.

### `users.csv`

| Column | Type | Description |
| --- | --- | --- |
| `user_id` | string | Unique enterprise / organisation id |
| `region` | string | Region id; used by the `URU` meta-path |
| `industry` | string | Optional; not used by the reference model |

### `businesses.csv`

| Column | Type | Description |
| --- | --- | --- |
| `business_id` | string | Unique testing / inspection provider id |
| `region` | string | Region id; used by region-aware meta-paths such as `BRB` |

### `services.csv`

| Column | Type | Description |
| --- | --- | --- |
| `service_id` | string | Unique inspection item id |
| `category` | string | Service category (informational) |
| `standard_id` | string | Standard the service is accredited against |

### `business_services.csv`

| Column | Type | Description |
| --- | --- | --- |
| `business_id` | string | Must exist in `businesses.csv` |
| `service_id` | string | Must exist in `services.csv` |

This file defines the accreditation relation. It is usually the easiest file to obtain
from a business directory.

### `interactions.csv`

| Column | Type | Description |
| --- | --- | --- |
| `user_id` | string | Must exist in `users.csv` |
| `business_id` | string | Must exist in `businesses.csv` |
| `service_id` | string | Must exist in `services.csv` |
| `timestamp` | integer or sortable value | Used to order each user's history |

Example:

```csv
user_id,business_id,service_id,timestamp
U0000,B0044,S0002,20220105
U0000,B0052,S0006,20220113
U0001,B0012,S0018,20220107
```

## 2. Mapping a real testing-and-inspection database

| Domain entity | Node type | Typical source table |
| --- | --- | --- |
| Enterprise client | `user` | customer / contract table |
| Inspection provider | `business` | supplier / lab registry |
| Inspection item | `service` | service catalogue |
| Accreditation standard | `standard` | standard / certificate table |
| Province / city | `region` | address table |

Build the five CSVs from those tables; no feature engineering is required beyond
mapping identifiers to strings. Categories and industries are optional and can be kept
for analysis.

## 3. Split protocol

`leave_one_out_split` in [`hret/data/dataset.py`](../hret/data/dataset.py):

1. Group interactions by user.
2. Collapse repeated interactions with the same business to the latest occurrence.
3. Shuffle the remaining businesses (`data.split_strategy: random`, default) or sort them
   by timestamp (`data.split_strategy: temporal`).
4. The last business in that order is the test target; the second last is the validation
   target.
5. Users with fewer than `data.min_interactions` distinct businesses stay in training but
   are not evaluated.

During validation, training items are masked. During test, training **and** validation
items are masked. The model never sees held-out edges when the HIN is built.

If your data has no reliable timestamps, replace `timestamp` with a monotonically
increasing row number. Timestamps are only used by the optional temporal split; the
default random split does not rely on them.

## 4. Cold start

* A user with no training interaction is still reachable through `user–region`; the
  `user–service` edge only exists when the user has at least one training interaction.
  In practice such users are excluded from evaluation by `data.min_interactions`; for
  production cold start, add profile features as new node types or as attributes.
* A business with no training interaction can still be scored because it has
  `business–service` and `business–region` edges. Its embedding is driven by `BSB` and
  the static schema, not by user interactions.

## 5. The bundled sample

`data/sample` is **synthetic**, generated by
[`scripts/generate_synthetic.py`](../scripts/generate_synthetic.py):

* 240 users, 80 businesses, 24 services, 8 standards, 6 regions;
* 3,098 interactions;
* every user has a preferred inspection category and a region;
* interaction probability increases with category match, region match and a per-user
  preference strength;
* noise is added so that the task is not trivially separable.

It is small enough to commit and fast enough for CI. Regenerate it with:

```bash
python scripts/generate_synthetic.py --out data/sample --seed 42
```

Do not report results on this sample as scientific evidence.
